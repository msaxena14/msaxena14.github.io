Redis auth switched on but KEDA scalers still sent an empty password

After Redis authentication was enabled, every KEDA scaler still connected without a password, so nothing scaled and a shared queue backed up to about 600,000 messages.

 Critical · Client prod

Symptom

KEDA scaling failed for every microservice of a multi-service application, across the Azure client environments. Pods stopped scaling out, and a work queue that another service depends on piled up to about 600,000 messages. A Critical ticket was open.

Investigation

The error on the ScaledObjects was connection to redis failed: NOAUTH Authentication required. That means KEDA reached Redis but sent no credentials. Redis authentication had recently been switched on, but the chart's Redis triggers still had an empty password setting, so each trigger connected unauthenticated and was refused. The same blank value appeared in seven autoscaler templates across five subcharts, which made it a chart-level problem, not something to fix per client.

Fix

One chart change across the seven templates: each Redis trigger now sets the password environment variable and references the existing secret-backed TriggerAuthentication, so KEDA authenticates with the same credentials the services already use. The change was opened and merged within minutes.

Impact

The ScaledObjects went healthy and autoscaling resumed, about 12 minutes from the ticket being raised to the fix being confirmed. It was checked on the client where it was reported and on two others.

Missing Kubernetes Service silently breaks customer callbacks

Exports reported success internally, but the customer's callbacks never fired. Traced to a Helm chart that only created the Service under one network topology.

 Critical · Client staging

Symptom

On a client staging environment, customer callback notifications never fired, even though exports were marked successful internally. A Critical ticket was open and the customer was blocked.

Investigation

Both services were healthy, which ruled out crashes and scheduling. The application logs showed repeated DNS failures (Name or service not known) when one service tried to reach another. Checking the cluster confirmed the target had no Kubernetes Service, so nothing could resolve it. The Helm chart only created that Service under a conditional intended for a different network topology, so environments outside that topology never got one.

Fix

Drove a chart change adding an unconditional Service template, reviewed and merged it, and had it deployed through the GitOps pipeline.

Impact

DNS resolution was restored, callbacks fired again, and the customer was unblocked.

Misleading allow-list error hides a stale image tag

A pod restarted 12,000+ times behind an "IP not whitelisted" error. The allow-list was fine; a very old image tag was the real cause.

 Medium · Client prod

Symptom

A pod on a client's Azure cluster had restarted more than 12,000 times, a long-standing condition rather than a new regression. Its logs ended in ConnectionError: Customer IP is not whitelisted against an Azure OpenAI endpoint.

Investigation

The error read like a network allow-list gap, and the first step was to ask for the client's egress IP. A teammate questioned that: the service calls the endpoint from the cluster, not from the customer's network. Checking the cluster's NAT gateway address against the endpoint's network rules showed it was already allow-listed, which disproved the hypothesis. With networking ruled out, comparing the deployed version with current releases showed the service was running a very old image tag, and together with the owning team that became the most likely cause.

Fix

Upgraded the service to a current release through the GitOps configuration.

Impact

The pods came up and stayed up with no restarts, ending a restart loop that had run for more than two weeks.

Autoscaled neighbour exhausts the shared database connection slots

Synthetic 500s on a user-management service traced to a neighbouring service autoscaling and consuming the shared database's connection slots.

 Medium · Client staging

Symptom

Synthetic checks against a staging user-management service started returning HTTP 500. The service's logs showed Postgres refusing connections: remaining connection slots are reserved for roles with the SUPERUSER attribute.

Investigation

That error means the database has run out of regular connection slots, so the question was who was holding them. A traffic spike on a separate document-processing service had scaled it to about 27 pods. Each pod keeps its own connection pool of roughly 10 connections, around 291 in total, against a server limit of 401. With about 384 connections in use, user management lost the race for the last slots. The headroom was only a few connections, so the next spike would repeat the failure.

Fix

Recommended three options, in order of effort: cap the per-pod pool size, raise max_connections, and put a connection pooler such as PgBouncer between the applications and the database. The owning application team applied the fix under a separate ticket.

Impact

The incident was closed with a documented root cause and a clear way to stop it recurring on the next traffic spike.

ImagePullBackOff from a chart default pointing at a missing image

A pod stuck in ImagePullBackOff because the chart's default image path no longer existed in the registry.

 Medium · Client prod

Symptom

A UI-shell service sat in ImagePullBackOff for the whole alert window on a client's production cluster.

Investigation

The ImagePull error and ECR registry showed that the referenced image path and tag did not exist at all, so retries could never succeed. The path came from the chart's default values, not from anything specific to the client. A developer confirmed the service shouldn't use that default and supplied the correct repository and tag.

Fix

Added a per-client override for the image repository and tag, merged it, promoted it, and let the GitOps sync roll it out.

Impact

The deployment synced and went healthy, with pods running without restarts or errors. The UI was checked after logging in to confirm it served correctly.

  • ECR
  • Helm
